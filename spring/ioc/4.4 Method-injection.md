# Method Injection

Method Injection is an advanced Spring IoC feature designed to solve a very specific problem: **Dependency Scope Mismatches**.

## 1. The Problem: Singleton depends on Prototype

In most applications, beans are singletons. If a singleton depends on another singleton, everything works perfectly. 

However, a problem arises when a **Singleton bean (A)** needs to use a **Prototype bean (B)** on every method invocation.
Because Bean A is a singleton, the container creates it only *once* and injects its dependencies only *once*. Therefore, Bean A gets stuck with the exact same instance of Bean B forever, completely defeating the purpose of the prototype scope!

### The "Bad" Solution (Tight Coupling)
You could make your Singleton implement `ApplicationContextAware` and manually call `context.getBean("prototypeBean")` every time you need it. 
**Why it's bad:** Your pure business code is now tightly coupled to the Spring Framework API, making it harder to unit test and maintain.

---

## 2. The Clean Solution: `@Lookup` Method Injection

Lookup Method Injection allows the Spring container to dynamically override a method on your bean at runtime. When you call this overridden method, Spring automatically fetches a brand-new instance of the prototype bean for you.

Spring achieves this by using CGLIB bytecode generation to dynamically subclass your bean on the fly.

> [!WARNING]
> **Limitations of @Lookup:**
> 1. The class **cannot** be `final`.
> 2. The lookup method **cannot** be `final`.
> 3. It **does not work** with `@Bean` factory methods in `@Configuration` classes (because Spring is not in charge of creating the instance itself, so it cannot generate the runtime subclass).

### Code Demo: `@Lookup`

Instead of coupling your code to Spring's `ApplicationContext`, you simply define an `abstract` method and annotate it with `@Lookup`.

```java
// Notice: No Spring API imports required for the core business logic!
public abstract class CommandManager {

    public Object process(Object commandState) {
        // 1. Call the abstract method. 
        // Spring's dynamic subclass intercepts this and returns a NEW prototype instance!
        Command command = createCommand();
        
        command.setState(commandState);
        return command.execute();
    }

    // 2. Spring implements this method automatically at runtime.
    // It knows exactly which bean to fetch based on the return type (Command).
    @Lookup
    protected abstract Command createCommand();
}
```

*Note: You can also explicitly name the bean to fetch by using `@Lookup("myCommandBeanName")`.*

---

## 3. Arbitrary Method Replacement (Rare Use Case)

A far less common form of method injection is **Arbitrary Method Replacement**. This allows you to completely replace the implementation of *any* method in a managed bean without modifying its source code.

> [!NOTE]
> You can safely ignore this feature unless you are dealing with legacy XML code where you absolutely must override a method's behavior but cannot change the original compiled class.

### How it works (XML)
1. You write a class that implements Spring's `MethodReplacer` interface and put the new logic in its `reimplement()` method.
2. In your XML configuration, you use the `<replaced-method>` tag to tell Spring to swap the original method with your `MethodReplacer` bean.

```xml
<bean id="myValueCalculator" class="x.y.z.MyValueCalculator">
    <!-- Replace the computeValue(String) method with our custom bean -->
    <replaced-method name="computeValue" replacer="replacementComputeValue">
        <arg-type>String</arg-type>
    </replaced-method>
</bean>

<bean id="replacementComputeValue" class="a.b.c.ReplacementComputeValue"/>
```
