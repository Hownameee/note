# Visualizing Beans in Spring Boot Admin (SBA)

To truly understand how Spring manages beans (names, scopes, and dependencies), there is no better way than visualizing them in Spring Boot Admin.

Below is a set of "test cases" designed specifically to highlight different `BeanDefinition` properties. If you run this code in a Spring Boot application connected to an Admin Server, you will see exactly how Spring registers and views them internally.

---

## The Demo Code

You can copy and paste the following classes directly into any configuration class in your Spring Boot application.

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Lazy;
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;
import org.springframework.stereotype.Repository;
import org.springframework.stereotype.Service;

@Configuration
public class BeanDemoConfig {

    // ---------------------------------------------------------
    // TEST CASE 1: Dependency Injection (Visualizing the Graph)
    // ---------------------------------------------------------
    
    @Repository
    public static class OrderRepository {
        // Standard singleton repository
    }

    @Component
    public static class PaymentGateway {
        // Standard singleton component
    }

    @Service
    public static class OrderService {
        private final OrderRepository orderRepository;
        private final PaymentGateway paymentGateway;

        // Spring injects these dependencies automatically
        public OrderService(OrderRepository orderRepository, PaymentGateway paymentGateway) {
            this.orderRepository = orderRepository;
            this.paymentGateway = paymentGateway;
        }
    }

    // ---------------------------------------------------------
    // TEST CASE 2: Bean Scopes (Singleton vs Prototype)
    // ---------------------------------------------------------
    
    @Component
    @Scope("singleton") // Explicitly stated, though this is the default
    public static class GlobalConfiguration {
    }

    @Component
    @Scope("prototype")
    public static class UserSessionCache {
    }

    // ---------------------------------------------------------
    // TEST CASE 3: Naming, Aliasing, and Lazy Initialization
    // ---------------------------------------------------------
    
    @Bean(name = {"primaryDatabase", "legacyDatabaseAlias"})
    public String databaseConnectionBean() {
        return "jdbc:mysql://localhost:3306/mydb";
    }

    @Component
    @Lazy
    public static class HeavyStartupService {
        public HeavyStartupService() {
            System.out.println("Heavy service instantiated!");
        }
    }
}
```

---

## Expected Output in Spring Boot Admin

Once your application starts and connects to Spring Boot Admin, navigate to the **"Beans"** tab. SBA reads from the `/actuator/beans` endpoint and displays the raw `BeanDefinition` metadata. Here is exactly what you will see for the test cases:

### 1. Visualizing Dependencies (`orderService`)
If you search for `orderService` in the SBA UI, you will see a visual representation of its dependencies.
*   **Bean Name:** `orderService`
*   **Scope:** `singleton`
*   **Dependencies:** Under the "Dependencies" section, SBA will list `orderRepository` and `paymentGateway`. 
    *   **The Takeaway:** This proves that Spring parses the constructor, understands the required types, and builds a Dependency Graph, knowing it must instantiate the repository and gateway *before* the service.

### 2. Identifying Scopes (`userSessionCache`)
If you search for `userSessionCache`:
*   **Bean Name:** `userSessionCache`
*   **Scope:** `prototype`
    *   **The Takeaway:** While almost every other bean in the list (including Spring's own internal beans) will say `singleton`, SBA clearly highlights that this specific bean definition is registered as a `prototype`. Spring knows it must bypass the singleton cache and generate a new instance upon request.

### 3. Names and Aliases (`primaryDatabase`)
If you search for `primaryDatabase`:
*   **Bean Name:** `primaryDatabase`
*   **Aliases:** `[ "legacyDatabaseAlias" ]`
    *   **The Takeaway:** Even though we only returned a simple `String` from our `@Bean` method, Spring registered it as a full-fledged bean. You will see both the primary name and the alias array clearly listed.

### 4. Lazy Initialization (`heavyStartupService`)
If you search for `heavyStartupService`:
*   **Bean Name:** `heavyStartupService`
    *   **The Takeaway:** You **will** see this bean in the list! Why? Because SBA pulls from the `BeanDefinition` registry (the metadata), not the instance pool. Spring knows the *definition* of this bean exists. However, if you look at your application's console output, you will **not** see `"Heavy service instantiated!"` printed. This perfectly proves that while the metadata is registered, the actual instantiation is delayed until another bean asks for it.
