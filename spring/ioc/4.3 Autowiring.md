# Autowiring Collaborators

The Spring container can automatically resolve and inject collaborators (other beans) into your beans. This significantly reduces the need to specify properties or constructor arguments manually.

**Advantages of Autowiring:**
*   Reduces boilerplate configuration.
*   Automatically updates dependencies as your classes evolve during development without needing configuration file changes.

---

## 1. Autowiring Modes

When using XML configuration, you can specify the autowiring mode per bean using the `autowire` attribute. 

| Mode | Explanation |
| :--- | :--- |
| **`no`** (Default) | No autowiring. You must use `<ref>` to explicitly define dependencies. *Recommended for large systems because it acts as explicit documentation of the architecture.* |
| **`byName`** | Autowires by property name. Spring looks for a bean in the container with the exact same name as the property being set (e.g., for `setMaster(...)`, it looks for a bean named `master`). |
| **`byType`** | Autowires if there is **exactly one** bean of the required type in the container. If more than one exists, a fatal exception is thrown. |
| **`constructor`** | Analogous to `byType`, but applies to constructor arguments. Throws an error if there isn't exactly one bean of the argument type. |

> [!TIP]
> **Autowiring Collections:** When using `byType` or `constructor` modes, you can wire arrays, Collections, or Maps. Spring will automatically inject **all** beans in the container that match the expected type. For a `Map<String, MyType>`, the map keys will automatically be populated with the respective bean names.

---

## 2. Limitations and Disadvantages

While powerful, autowiring has some strict limitations by design:

*   **Explicit Overrides:** Explicit property and constructor-arg settings always override autowiring.
*   **No Simple Types:** You **cannot** autowire primitives (e.g., `int`), `String`, or `Class` types (nor arrays of them).
*   **Less Explicit:** Autowiring acts like "magic". The exact relationships between your objects are no longer explicitly documented in your configuration files.
*   **Ambiguity Exceptions:** If a dependency expects a single value, but multiple beans of that type exist in the container, Spring refuses to guess arbitrarily and throws an exception.

### Resolving Ambiguity
If you have multiple beans of the same type and autowiring fails, you can:
1.  Abandon autowiring and use explicit wiring.
2.  Designate one bean as the primary candidate (`primary="true"` in XML, or `@Primary` in Java).
3.  Exclude specific beans from being autowired (see below).
4.  Use finer-grained annotation control (e.g., `@Qualifier`).

---

## 3. Excluding a Bean from Autowiring

You can completely hide a specific bean from the autowiring infrastructure so it never gets injected into other beans automatically.

> [!NOTE]
> Excluding a bean only prevents it from being injected into *other* beans via type-matching. The excluded bean itself can still have its own dependencies autowired. It also does not stop explicit injection by *name*.

### How to Exclude
*   **XML:** Set `autowire-candidate="false"` on the `<bean/>` element.
*   **Java Config:** Set `autowireCandidate = false` on the `@Bean` annotation.

#### Pattern Matching (XML)
You can limit autowiring candidates to specific naming patterns at the top level of your XML file:
`<beans default-autowire-candidates="*Repository">` 
*(This means only beans ending in "Repository" will be considered for autowiring).*

### New in Spring 6.2: `defaultCandidate`
As of Spring 6.2, `@Bean` methods support a more nuanced exclusion flag:
1.  **`autowireCandidate=false`**: The bean is completely hidden from type-based autowiring.
2.  **`defaultCandidate=false`**: The bean is hidden from *plain* type-based autowiring, but **can** still be injected if the injection point explicitly requests it using a specific `@Qualifier`. This is highly useful for specific delegate classes.

## 4. Code Demonstrations

### Autowiring Collections & Maps
If you have multiple beans of the same type, you can automatically gather them all into a List or a Map.

```java
@Component
public class ValidationService {

    // Spring finds ALL beans implementing 'Validator' and injects them into this list.
    @Autowired
    private List<Validator> allValidators;

    // The Map key will be the bean's name (e.g., "emailValidator"), 
    // and the value will be the bean instance itself.
    @Autowired
    private Map<String, Validator> validatorMap;
}
```

### Resolving Ambiguity with `@Primary`
When multiple beans of the same type exist, Spring will throw an error when trying to autowire a single instance unless you mark one as `@Primary`.

```java
@Configuration
public class DatabaseConfig {

    @Bean
    @Primary // Tells Spring: "If someone asks for a DataSource, give them this one!"
    public DataSource primaryDataSource() {
        return new HikariDataSource();
    }

    @Bean
    public DataSource reportingDataSource() {
        return new HikariDataSource();
    }
}
```

### Excluding a Bean from Autowiring
If you want to ensure a bean is never accidentally injected into another component by its type.

```java
@Configuration
public class SecurityConfig {

    // This encoder will exist in the container, but Spring will IGNORE it 
    // when performing type-based autowiring (e.g. @Autowired PasswordEncoder).
    @Bean(autowireCandidate = false)
    public PasswordEncoder legacyPasswordEncoder() {
        return new Md5PasswordEncoder(); 
    }
}
```
