# Bean Configuration and Stereotypes

This guide covers the differences between Java Configuration and Annotation-based Configuration, as well as a deep dive into Spring's core stereotype annotations.

---

## 1. Java Configuration vs. Annotation Configuration

Both approaches use annotations, but they represent two fundamentally different ways of telling Spring how to create beans. In a modern Spring Boot application, you will almost always use **both**. 

### A. Annotation-Based Configuration (Implicit / Component Scanning)
This is when you put annotations **directly on the classes you write**.

*   **How it works:** You annotate your classes with `@Component`, `@Service`, `@Repository`, or `@Controller`. You then tell Spring to scan your packages (usually handled automatically by `@SpringBootApplication`). Spring finds these classes, creates them, and wires their dependencies automatically.
*   **When to use it:** For **your own code**. If you are writing a business service or a web controller, this is the best and fastest way.
*   **Example:**
    ```java
    // You wrote this class, so you just drop an annotation on it.
    @Service 
    public class MyBusinessService {
        // Spring automatically creates this and injects any dependencies
    }
    ```

### B. Java Configuration (Explicit / Factory Methods)
This is when you write a separate configuration class to manually create and return objects.

*   **How it works:** You create a class annotated with `@Configuration`. Inside it, you write methods annotated with `@Bean`. Spring calls these methods, takes the object you return, and registers it as a Bean.
*   **When to use it:** 
    1.  **For Third-Party Code:** You cannot put a `@Component` annotation on a class you didn't write (like a `DataSource` from a database library). You *must* use `@Bean` to create them.
    2.  **Complex Setup:** When creating the object requires complex logic (e.g., checking environment variables) before returning it.
*   **Example:**
    ```java
    @Configuration
    public class AppConfig {
    
        // We cannot put @Component on HikariDataSource because we didn't write it.
        @Bean
        public DataSource dataSource() {
            HikariDataSource ds = new HikariDataSource();
            ds.setJdbcUrl("jdbc:mysql://localhost/test");
            return ds;
        }
    }
    ```

## 2. Spring Stereotype Annotations Deep Dive

At their core, `@Service`, `@Repository`, and `@Controller` are all just specializations of `@Component`. Functionally, they all tell the IoC container: *"Instantiate this class and manage it as a bean."*

Spring provides these different annotations for two reasons: **Semantic meaning** (readability for developers) and **Specialized technical behaviors**.

### A. `@Component` (The Parent)
*   **What it is:** The generic, base annotation for any Spring-managed component.
*   **When to use it:** Use this when a class doesn't neatly fit into the Service, Repository, or Controller layers (e.g., a custom utility class, a data converter, or an API wrapper).

### B. `@Service` (Business Logic)
*   **What it is:** A marker for the "Service Layer" where your core business logic lives.
*   **Technical Difference:** None. Functionally, it behaves exactly like `@Component`.
*   **Why use it?** It strictly serves as a semantic marker. It immediately tells other developers, *"This class contains business rules."*

### C. `@Repository` (Data Access)
*   **What it is:** A marker for the "Data Access Layer" (DAOs). Classes that interact directly with databases.
*   **Technical Difference:** Unlike `@Service`, `@Repository` actually adds technical behavior. Spring automatically enables **Exception Translation** for classes marked with `@Repository`. 
    *   *What does that mean?* If your database throws a vendor-specific error (like a `HibernateException`), Spring catches it and translates it into Spring's own unified `DataAccessException`. This allows your business logic to handle database errors without being tightly coupled to a specific technology.

### D. `@Controller` / `@RestController` (Web/Presentation Layer)
*   **What it is:** A marker for the "Presentation Layer". These classes handle incoming HTTP requests.
*   **Technical Difference:** Spring's web engine (`DispatcherServlet`) specifically hunts for classes annotated with `@Controller` or `@RestController`. It scans these classes for URL routing annotations like `@GetMapping`. 
    *   *Note:* If you annotate a web controller with `@Component` instead of `@Controller`, Spring will create the bean, but it **will not** map HTTP requests to its methods.

### Summary Table

| Annotation | Application Layer | Technical Behavior Added Beyond `@Component` |
| :--- | :--- | :--- |
| **`@Component`** | Any generic layer | None (Base annotation) |
| **`@Service`** | Business Logic Layer | None (Purely for semantic readability) |
| **`@Repository`**| Data Access Layer | **Yes:** Automatic translation of database exceptions. |
| **`@Controller`**| Web / HTTP Layer | **Yes:** Makes the class visible to the Web Servlet for HTTP routing. |
