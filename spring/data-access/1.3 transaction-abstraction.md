# Spring Transaction Abstraction

Spring abstracts transaction management through a clean API, separating the transaction definition from the actual underlying transaction engine (JDBC, JPA, JTA, Hibernate). This design allows for seamless switching between local and global transaction strategies without modifying business code.

---

## 1. Core Interfaces of the Abstraction

The core of Spring's transaction model relies on three key interfaces:

### A. `PlatformTransactionManager` (Imperative / Blocking)
This interface defines the transaction strategy for blocking (imperative) applications.

```java
public interface PlatformTransactionManager extends TransactionManager {
    // 1. Get or create a transaction based on definition properties
    TransactionStatus getTransaction(TransactionDefinition definition) throws TransactionException;

    // 2. Commit the transaction
    void commit(TransactionStatus status) throws TransactionException;

    // 3. Rollback the transaction
    void rollback(TransactionStatus status) throws TransactionException;
}
```

### B. `ReactiveTransactionManager` (Non-blocking)
Used for reactive applications (such as Spring WebFlux) leveraging Project Reactor (`Mono`/`Flux`) or Kotlin Coroutines.

```java
public interface ReactiveTransactionManager extends TransactionManager {
    Mono<ReactiveTransaction> getReactiveTransaction(TransactionDefinition definition) throws TransactionException;
    Mono<Void> commit(ReactiveTransaction status) throws TransactionException;
    Mono<Void> rollback(ReactiveTransaction status) throws TransactionException;
}
```

### C. The Unchecked Exception Philosophy
All transaction-related exceptions (subclasses of `TransactionException`) are **unchecked** (`RuntimeException`). This ensures that developers are not forced to write boilerplate `try-catch` blocks for fatal database/infrastructure errors, keeping business code clean.

---

## 2. Transaction Parameters & Status

### A. `TransactionDefinition` (The Settings)
This interface defines the transactional properties:

1.  **Propagation:** Defines how a transaction behaves if one already exists in the current execution stack (e.g., join the active transaction, suspend it and start a new one).
2.  **Isolation:** The isolation level from concurrent transactions (e.g., Dirty Reads prevention, Repeatable Reads).
3.  **Timeout:** The maximum duration before the transaction times out and auto-rolls back.
4.  **Read-Only Status:** Optimization flag for transactions that only perform read operations (highly optimized in Hibernate).

### B. `TransactionStatus` (The State Tracker)
Tracks the state of the current transaction and allows programmatic rollback control.

```java
public interface TransactionStatus extends TransactionExecution, SavepointManager, Flushable {
    boolean isNewTransaction(); // True if this method call started the transaction
    boolean hasSavepoint();     // True if nested transaction savepoints are present
    void setRollbackOnly();     // Force transaction to rollback (cannot be committed)
    boolean isRollbackOnly();   // Check if it's marked for rollback-only
    void flush();               // Flush session changes to the DB
    boolean isCompleted();      // Check if transaction has finished (committed or rolled back)
}
```

## 3. Concrete Implementations & Setup Examples

Depending on the technology stack, you define the appropriate `PlatformTransactionManager` bean inside the Spring IoC container.

### A. Plain JDBC Setup (Local)
Uses `DataSourceTransactionManager` which requires a reference to the `DataSource`.

```xml
<!-- 1. Define the DataSource -->
<bean id="dataSource" class="org.apache.commons.dbcp.BasicDataSource" destroy-method="close">
    <property name="url" value="${jdbc.url}" />
    <property name="username" value="${jdbc.username}" />
    <property name="password" value="${jdbc.password}" />
</bean>

<!-- 2. Define the Transaction Manager -->
<bean id="txManager" class="org.springframework.jdbc.datasource.DataSourceTransactionManager">
    <property name="dataSource" ref="dataSource"/>
</bean>
```

### B. Hibernate Setup (Local)
Uses `HibernateTransactionManager` which needs a reference to Hibernate's `SessionFactory`.

```xml
<bean id="sessionFactory" class="org.springframework.orm.jpa.hibernate.LocalSessionFactoryBean">
    <property name="dataSource" ref="dataSource"/>
    <property name="hibernateProperties">
        <value>hibernate.dialect=${hibernate.dialect}</value>
    </property>
</bean>

<bean id="txManager" class="org.springframework.orm.jpa.hibernate.HibernateTransactionManager">
    <property name="sessionFactory" ref="sessionFactory"/>
</bean>
```

### C. JTA Setup (Global / Multi-Resource)
For global transactions managed by a Jakarta EE Application Server, Spring utilizes `JtaTransactionManager`. 
*The JtaTransactionManager does not need references to specific DataSources or SessionFactories, because it delegates global coordination entirely to the container's JTA engine.*

```xml
<!-- Lookup the container-managed DataSource via JNDI -->
<jee:jndi-lookup id="dataSource" jndi-name="jdbc/myStore"/>

<!-- JtaTransactionManager delegates to the app server automatically -->
<bean id="txManager" class="org.springframework.transaction.jta.JtaTransactionManager" />
```

> [!NOTE]
> Even if you switch from a Local JDBC setup to a Global JTA setup, **no changes are needed in your Java code**. You only modify the configuration metadata (XML or Java `@Configuration` beans). This is the power of Spring's transaction abstraction.
