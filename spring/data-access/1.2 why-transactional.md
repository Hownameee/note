# Why manage transactions in Spring instead of the Database?

While you *can* write transactions directly inside the database using Stored Procedures (`BEGIN`, `COMMIT`, `ROLLBACK`), modern software architecture almost universally prefers managing transactions in the Application Layer (Spring). Here is why:

1.  **Business Logic Resides in the Application:** A transaction often spans more than just database tables. What if you need to deduct money, create an order, and *then publish a message to RabbitMQ* or *call the Stripe REST API*? A database stored procedure cannot make HTTP calls. The application layer orchestrates the entire workflow.
2.  **Cross-Database (Distributed) Transactions:** If your app uses PostgreSQL for user data and MongoDB for product catalogs, a transaction inside Postgres cannot roll back MongoDB. Spring can coordinate multi-system transactions.
3.  **Database Portability:** If you write 100 transactions in PL/pgSQL (Postgres) and later migrate to MySQL or Oracle, you must rewrite all of them. Spring's `@Transactional` works identically regardless of the underlying DB vendor.
4.  **Testing & Version Control:** Java code is incredibly easy to unit test (mocking the DB) and version control. Testing stored procedures is notoriously difficult, slow, and hard to integrate into modern CI/CD pipelines.
5.  **Exception Handling:** In Java, you can catch a specific exception, wrap it in a custom `UserAlreadyExistsException`, log it to an external observability service, and roll back. Doing complex error routing inside raw SQL is incredibly clunky.
