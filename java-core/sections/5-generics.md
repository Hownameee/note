# 5. Generics

Generics provide **compile-time type safety** and eliminate manual type casting when writing reusable algorithms and data structures.

```java
static <T> T first(List<T> values) {
    if (values.isEmpty()) throw new NoSuchElementException();
    return values.get(0);
}
```

---

### Invariance and Wildcards (PECS)

Java generic types are **invariant**: `List<Integer>` is **NOT** a subtype of `List<Number>`. 
*(If it were allowed, you could add a `Double` into a `List<Number>` reference pointing to an integer list, corrupting type safety).*

Use **wildcards** to express variance at API boundaries:

#### 1. Upper Bounded Wildcard (`? extends T`) — Covariance (Producer)
* **Rule**: You can safely **read** items as `T`. You **cannot add** items (except `null`) because the compiler cannot guarantee the specific concrete subtype.
* Used when the collection **produces** data for your method.

#### 2. Lower Bounded Wildcard (`? super T`) — Contravariance (Consumer)
* **Rule**: You can safely **add** instances of `T` (and its subtypes). Items **read** out are only known to be `Object`.
* Used when the collection **consumes** (stores) data provided by your method.

#### 3. PECS Principle: *Producer Extends, Consumer Super*
```java
// Reads from 'source' (Producer -> extends) and writes to 'target' (Consumer -> super)
public static <T> void copy(List<? extends T> source, List<? super T> target) {
    for (T item : source) {
        target.add(item);
    }
}
```

---

### How Generics Work Under the Hood: Type Erasure

Java Generics are largely a **compile-time mechanism**. The JVM runtime has almost no knowledge of generic type arguments.

```
Your Java Source Code (with <T>)
        │
        ▼
1. Compile-Time Type Checking (javac verifies type safety)
        │
        ▼
2. Type Erasure (javac strips <T>, replaces with Object or upper bound)
        │
        ▼
3. Bytecode Cast Insertion (javac inserts explicit `checkcast` instructions)
        │
        ▼
4. Bridge Method Generation (javac creates synthetic methods for polymorphism)
        │
        ▼
Compiled Bytecode (.class) executed by JVM (pure raw types + casts)
```

#### 1. Erasure Rules
* **Unbounded parameters** (`<T>`) are erased to `java.lang.Object`.
* **Bounded parameters** (`<T extends Number>`) are erased to their first bound (`Number`).
* **Multiple bounds** (`<T extends Number & Comparable<T>>`) erase to the first bound (`Number`), while the compiler inserts interface casts for `Comparable` where necessary.

#### 2. Bytecode Cast Insertion
**Source code:**
```java
List<String> list = new ArrayList<>();
list.add("hello");
String s = list.get(0);
```

**Bytecode equivalent emitted by `javac`:**
```java
List list = new ArrayList();
list.add("hello");
String s = (String) list.get(0); // Compiler automatically adds checkcast
```

#### 3. Synthetic Bridge Methods
When a class implements or extends a parameterized type, erasure can cause method signature mismatches. The compiler generates **synthetic bridge methods** to preserve runtime polymorphism.

```java
// Source:
public class StringSupplier implements Supplier<String> {
    @Override
    public String get() { return "data"; }
}

// Bytecode generated by javac:
public class StringSupplier implements Supplier {
    public String get() { return "data"; }

    // Generated bridge method to satisfy Supplier interface:
    public Object get() {
        return this.get(); // calls String get()
    }
}
```

#### 4. Why was it designed with Type Erasure?
* **Backward Compatibility**: When Generics were introduced in Java 5 (2004), millions of lines of pre-existing Java 1.4 code used raw types (`List list = new ArrayList()`).
* Type erasure ensured **100% binary compatibility**: legacy libraries and new generic code could run together on the same JVM without altering bytecode execution engines.

---

### Consequences and Restrictions of Type Erasure

Because generic types are erased at runtime:

| Restriction | Why it occurs | Correct Alternative |
| :--- | :--- | :--- |
| **No `new T()`** | At runtime, `T` is `Object`; JVM does not know which constructor to invoke. | Pass a `Supplier<T>` or `Class<T>` factory (`clazz.getDeclaredConstructor().newInstance()`). |
| **No `instanceof List<String>`** | At runtime, all generic instances share the same raw class (`List.class`). | Check raw type: `o instanceof List<?>`. |
| **No `new T[10]` or `new List<String>[10]`** | Java arrays are *reified* (check types at runtime); Generics are *erased* (checked at compile-time). Mixing them leads to Heap Pollution. | Use `List<T>` or `(T[]) Array.newInstance(clazz, size)`. |
| **No primitive type arguments (`List<int>`)** | `T` erases to `Object`; primitive types do not inherit from `java.lang.Object`. | Use wrapper types (`List<Integer>`) or specialized primitive collections. |
| **Cannot overload methods by generic type alone** | `void print(List<String> l)` and `void print(List<Integer> l)` both erase to `void print(List l)`. | Use distinct method names: `printStrings(...)` and `printIntegers(...)`. |
| **No static fields of type `T`** | A static field is shared across all instances of the class; `T` is per-instance. | Use instance fields or separate non-generic static containers. |

---

### Preserved Type Metadata (Reflection)

While instances on the Heap do not retain generic arguments, `javac` records generic signatures in the **`Signature` attribute** of the `.class` file constant pool for:
* Class declarations (`class Box<T>`)
* Field declarations (`List<String> items`)
* Method parameters and return types (`List<T> find(String key)`)

This metadata is readable at runtime via Reflection (`ParameterizedType.getActualTypeArguments()`) and is used by frameworks (Spring, Jackson, Gson) for dependency injection and JSON serialization.
